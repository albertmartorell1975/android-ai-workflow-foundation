# Module Architecture Specialist (`module-architecture-governance`)

This skill ensures that the project's multi-module structure remains healthy and strictly follows Clean Architecture boundaries across both **Layer-Based** and **Feature-First** topologies.

> [!IMPORTANT]
> **Reference Values (SDKs)**: SDK Versions (`minSdk`, `targetSdk`, `compileSdk`) MUST be dynamically resolved. The Android Studio New Project Wizard typically defines `minSdk` and `targetSdk`/`compileSdk` inside `:app/build.gradle.kts` upon project creation. Agents MUST check `gradle/libs.versions.toml` first, and if not present there, strictly extract the exact values generated by the wizard in the `:app` module.
> **Reference Values (Java)**: **Java 17 (JDK 17) is the MANDATORY minimum baseline** for modern tooling (AGP 8.x+) and Kotlin 2.0+ (K2) performance. However, if the project is already using a newer version (e.g., Java 21) in `:app` or `libs.versions.toml`, agents MUST detect and apply that newer version to all new modules to ensure consistency.

## 1. Topology Detection & Modularization Strategy

Before creating or modifying modules, the agent MUST inspect `settings.gradle.kts` and `AGENTS.md` to identify the active **Module Topology**:

* **Topology A — Horizontal Layer-Based (Default for PoCs / Small Apps)**:
  - Uses 4 horizontal root modules: `:domain`, `:usecases`, `:data`, and `:app`.
  - Best for lean projects and didactic enforcement of Clean Architecture boundaries.
* **Topology B — Vertical Feature-First (For Scalable / Multi-Feature Apps)**:
  - Organizes code by feature directory (`/<feature>/`), where each feature has 4 independent Gradle sub-modules:
    * `:<feature>:domain` (Pure Kotlin/JVM)
    * `:<feature>:usecases` (Pure Kotlin/JVM)
    * `:<feature>:data` (Android Library, no UI)
    * `:<feature>:presentation` (Android Library with Compose UI & ViewModels)
  - Shared domain-agnostic toolboxes live in `:core:*` (`:core:common`, `:core:network`, `:core:database`, `:core:designsystem`).
  - `:app` acts strictly as a thin **Integrator** (wiring `NavHost` to `:<feature>:presentation` and DI bindings to `:<feature>:data`).
  - Maximizes Gradle *Compilation Avoidance* and prevents merge conflicts when **`workflow-orchestrator`** executes multiple features in parallel `git worktree` instances.

> [!NOTE]
> For full architectural rules on migrating to or building **Feature-First Modules** (`:<feature>:*` and `:core:*`), read **[Feature Modularization Strategy](references/feature-modularization-strategy.md)**.

## 2. Golden Rules (Mandatory Across Both Topologies)

1. **The Trinity of Purity**:
   - `domain` (`:domain` or `:<feature>:domain`) and `usecases` (`:usecases` or `:<feature>:usecases`) MUST be **pure Kotlin/JVM** modules (`alias(libs.plugins.kotlin.jvm)` — no `android {}` block allowed).
   - `data` (`:data` or `:<feature>:data`) MUST be an Android Library (`com.android.library`) to support Room/DataStore/network infrastructure, and MUST NOT contain any UI dependencies (Compose or Views).
   - JSR-330 (`javax.inject`) is the permitted dependency for framework-agnostic Dependency Injection across `domain` and `usecases`.
2. **UI & Presentation Isolation**:
   - In **Layer-Based** topology: `:app` hosts the UI layer (Compose), framework entry points (`Activity`, `Application`), and DI wiring.
   - In **Feature-First** topology: `:<feature>:presentation` hosts feature UI screens, ViewModels, and feature-specific `.webp` drawable resources; shared UI components live in `:core:designsystem`; `:app` is strictly reserved for `MainActivity`, `Application`, root `NavHost`, and DI wiring (`:<feature>:presentation` + `:<feature>:data`).
3. **No Feature-to-Feature Horizontal Dependencies (Feature-First)**:
   - A feature sub-module (e.g., `:basket:*`) MUST NEVER depend on another feature sub-module (e.g., `:characters:*`). Shared cross-feature contracts belong in `:core:common` or `:core:model`.
4. **No Hardcoded Strings**: All Gradle plugins must be applied via `alias(libs.plugins.[name])`.
5. **Local Ignoring Mandate (STRICT)**: Every module and sub-module MUST have its own `.gitignore` file (`/build`) so build artifacts are never tracked by Git.

## 4. Operational Workflow

When asked to modularize, create new layers, or scaffold a new feature module:
1. **Audit**: Check `settings.gradle.kts` and `AGENTS.md` to confirm whether the project uses `Layer-Based` or `Feature-First` topology, and resolve SDK/Java versions from `gradle/libs.versions.toml` or `:app/build.gradle.kts`.
2. **Creation**: Read [Gradle Blueprints](references/gradle-blueprints.md) and apply the matching blueprint (`build.gradle.kts`) and local `.gitignore`.
3. **Structure**: Scaffold packages matching `com.example.<app>.<layer>` (Layer-Based) or `com.example.<feature>.<layer>` (Feature-First).
4. **Registration**: Add `include(...)` entries to `settings.gradle.kts`.
5. **Wiring**: Connect dependencies strictly following the DAG rules.
6. **Sync**: Execute Gradle Sync and verification via the `compiler` skill.
