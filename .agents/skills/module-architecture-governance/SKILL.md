# Module Architecture Specialist

This skill ensures that the project's multi-module structure remains healthy and strictly follows Clean Architecture boundaries.

> [!IMPORTANT]
> **Reference Values (SDKs)**: SDK Versions (`minSdk`, `targetSdk`, `compileSdk`) MUST be dynamically resolved. The Android Studio New Project Wizard typically defines the `minSdk` and `targetSdk`/`compileSdk` inside the `:app/build.gradle.kts` file upon project creation. Agents MUST check `libs.versions.toml` first, and if not present there, strictly extract the exact values generated by the wizard in the `:app` module.
> **Reference Values (Java)**: **Java 17 (JDK 17) is the MANDATORY minimum baseline** for modern tooling (AGP 8.x+) and Kotlin 2.0 (K2) performance. However, if the project is already using a newer version (e.g., Java 21) in the `:app` module or `libs.versions.toml`, agents MUST detect and apply that newer version to all new modules to ensure consistency.

## Modularization Strategy (Current vs. Future)

The agent MUST understand the project's evolution path regarding modularization:
*   **Current State (Layer-Based PoC)**: The project uses a horizontal Layer-Based architecture (`:app`, `:data`, `:domain`, `:usecases`). This is a didactic choice to strictly enforce Clean Architecture boundaries and is the default behavior for this skill.
*   **Future Scale (Feature-Based)**: For scalability, the project can transition to a vertical Feature-Based architecture.
> [!NOTE]
> For instructions on how to migrate to or build Feature Modules (e.g., `:feature:login`, `:core:network`), agents MUST read `references/feature-modularization-strategy.md`.

## Golden Rules (MANDATORY for Layer-Based)

1. **The Trinity of Purity**: `:domain` and `:usecases` MUST be **pure Kotlin/JVM** modules (No `android {}` block allowed). The `:data` module MUST be an Android Library (`com.android.library`) to support Android-specific data infrastructure like Room or DataStore, but it MUST NOT contain any UI dependencies (like Compose or Views). JSR-330 (`javax.inject`) is the permitted dependency for framework-agnostic Dependency Injection across layers.
2. **Implementation Strategy**: Data infrastructure and implementations (e.g., Room databases, DAOs, Retrofit services, Repository implementations) MUST reside in the `:data` module. The `:app` module is strictly reserved for the UI layer (Compose), framework entry points (Activity, Application), and Dependency Injection wiring.
3. **No Hardcoded Strings**: All plugins applied via `alias(libs.plugins.[name])`.
4. **Local Ignoring Mandate (STRICT)**: Every module MUST have its own `.gitignore` file to ensure build artifacts are not tracked by Git.

## Operational Workflow

When asked to modularize or create new layers:
1. **Audit**: Verify SDK/Java versions in `libs.versions.toml` or `:app/build.gradle.kts`. Ensure `javax.inject:javax.inject` is defined in the catalog for pure Kotlin DI.
2. **Creation**: Read the Gradle Blueprints from `references/gradle-blueprints.md` and apply them to the new module's `build.gradle.kts`. Ensure the local `.gitignore` is created.
3. **Structure**: Read `references/package-structure.md` to scaffold the correct packages.
4. **Registration**: Add `include(":module_name")` to `settings.gradle.kts`.
5. **Wiring**: Connect dependencies according to the blueprints.
6. **Sync**: Mandatory Gradle Sync via `compiler` skill.
